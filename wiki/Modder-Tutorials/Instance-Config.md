# Instance Config

The instance config system gives any mod a per-instance JSON file that drives the custom HUD shown in the dungeon, an optional system of difficulty/rule **modes** (mob scaling, drop list and block spawner swaps, time limit and PvP overrides, death-pipeline overrides, HUD mode tag), and an optional **portal image overlay** that floats in front of the source portal block while the destination world is alive.

If no config exists for an instance, the vanilla portal panel is shown and no modifiers apply. Everything in this file is opt-in.

## File Location

Place an `InstanceConfig.json` file inside your instance template folder:

```
Server/Instances/<your-instance-id>/InstanceConfig.json
```

The instance id is derived from the parent directory name automatically.

## Minimal Example

The minimum needed to enable the custom HUD for an instance:

```json
{
  "Hud": {}
}
```

With just `"Hud": {}`, the HUD will show automatically with:
- A title derived from the directory name (e.g., `My_Dungeon` becomes `My Dungeon`)
- No subtitle
- A default green timer bar if a time limit is set

## Full Example

```json
{
  "PortalParticleId": "MyMod_PortalOverlay_D01",
  "Hud": {
    "DisplayNameKey": "mymod.instance.my_dungeon.name",
    "SubtitleKey": "mymod.instance.subtitle",
    "DisplayNameColor": "#ca9f37",
    "SubtitleColor": "#af66ee",
    "TimerBarColor": "#79bd5f"
  },
  "Modes": {
    "Hardcore": {
      "DisplayNameKey": "mymod.instance.mode.Hardcore",
      "DisplayNameColor": "#d3384e",
      "Modifiers": {
        "TimeLimitSeconds": 1500,
        "IsPvpEnabled": true,
        "MobHealthMultiplier": 3.0,
        "MobDamageMultiplier": 2.0,
        "BossHealthMultiplier": 4.0,
        "BossDamageMultiplier": 2.0,
        "DropListReplacements": {
          "Drop_Skeleton_Burnt_Knight": "Drop_Skeleton_Burnt_Knight_Hardcore"
        },
        "BlockSpawnerReplacements": {
          "MyMod_Common_Chest": "MyMod_Common_Chest_Hardcore"
        },
        "DeathOverrides": {
          "RespawnController": "ExitInstance",
          "ItemsLossMode": "CONSUME"
        }
      }
    }
  }
}
```

## HUD

All fields inside `Hud` are optional.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `DisplayNameKey` | Translation key | Auto-generated from directory name | Translation key for the title shown at the top of the HUD |
| `SubtitleKey` | Translation key | None (hidden) | Translation key for a subtitle shown below the title |
| `DisplayNameColor` | Hex color | `#ca9f37` | Color of the title text |
| `SubtitleColor` | Hex color | `#af66ee` | Color of the subtitle text |
| `TimerBarColor` | Hex color | `#79bd5f` | Fill color of the countdown timer bar |

`DisplayNameKey` and `SubtitleKey` are translation keys, not raw strings. Add them to your language file at `Server/Languages/en-US/<YourMod>.lang`:

```
instance.my_dungeon.name = My Dungeon
instance.subtitle = My Mod
```

If `DisplayNameKey` is omitted, the title is auto-generated by title-casing the directory name (e.g., `My_Dungeon` → `My Dungeon`).

### HUD Position

By default the HUD uses `Auto` mode: it appears on the right side when no objectives are active, and moves to the left side when the player has active objectives (since the vanilla objective panel occupies the right side).

Server owners can override this in `FrameworkConfig.json` (at `mods/DanBagh_DungeonFramework/FrameworkConfig.json`):

```json
{
  "InstanceHudPosition": {
    "Mode": "Left"
  }
}
```

For full control over screen position, use `Custom` mode with explicit coordinates:

```json
{
  "InstanceHudPosition": {
    "Mode": "Custom",
    "X": 50,
    "Y": 150,
    "Width": 320
  }
}
```

Valid modes:

| Mode | Behavior |
|------|----------|
| `Auto` | Right when no objectives, left when objectives are active (default) |
| `Left` | Always on the left |
| `Right` | Always on the right |
| `Custom` | Fixed position using `X`, `Y`, and `Width` screen coordinates |

## Portal Image

Each instance can declare an image that floats in front of the portal block while the instance is active, the same look the Creative Hub portals (`Hub_Portal_Default`, `Hub_Portal_Flat`, `Hub_Portal_Zone3_Taiga1`) use to preview their destination. The image appears when a player summons this instance and goes away on its own when the instance ends or the portal block is broken.

### Top-Level Field

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `PortalParticleId` | Particle system id | None (vanilla portal, no overlay) | Id of a `.particlesystem` asset to render in front of the portal column while this instance's destination world is alive |

Omit the field to leave the portal looking vanilla.

### Authoring a Portal Image

A complete portal image needs three files plus an entry in your instance config. Names below assume an instance id of `MyMod_Instance_D01`, swap the suffix for your own.

#### 1. The Texture

Drop a 128x128 (or larger preserved-ratio) PNG with a transparent alpha channel at:

```
Common/Particles/Textures/MyMod/Portals/MyMod_PortalImage_D01.png
```

Vanilla's `Particles/Textures/Shapes/World_Flat.png` is a good reference for the style, a centered scene with the corners faded out to transparent so the image reads as a soft circle inside the portal column.

#### 2. The Particle Spawner

Create a `.particlespawner` file at:

```
Server/Particles/Portals/Spawners/MyMod_PortalImage_D01.particlespawner
```

Clone vanilla's `CreativeWorld_Default.particlespawner` and only change the `Texture` field to point at your PNG:

```json
{
  "RenderMode": "BlendAdd",
  "ParticleRotationInfluence": "None",
  "LinearFiltering": false,
  "LightInfluence": 0,
  "ParticleRotateWithSpawner": true,
  "TrailSpawnerPositionMultiplier": 1,
  "TrailSpawnerRotationMultiplier": 1,
  "MaxConcurrentParticles": 3,
  "ParticleLifeSpan": { "Min": 1.05, "Max": 2.033333333333333 },
  "SpawnRate": { "Min": 1.2, "Max": 3 },
  "InitialVelocity": { "Yaw": { "Min": -15, "Max": 15 }, "Pitch": { "Min": 80, "Max": 100 } },
  "Particle": {
    "Texture": "Particles/Textures/MyMod/Portals/MyMod_PortalImage_D01.png",
    "FrameSize": { "Width": 128, "Height": 128 },
    "ScaleRatioConstraint": "Preserved",
    "UVOption": "None",
    "Animation": {
      "0":   { "FrameIndex": { "Min": 0, "Max": 0 }, "Opacity": 0, "Scale": { "X": { "Min": 1, "Max": 1 }, "Y": { "Min": 1, "Max": 1 } }, "Rotation": { "X": { "Min": 0, "Max": 0 }, "Y": { "Min": 0, "Max": 0 }, "Z": { "Min": 0, "Max": 0 } } },
      "50":  { "Opacity": 1 },
      "100": { "Rotation": { "X": { "Min": 0, "Max": 0 }, "Y": { "Min": 0, "Max": 0 }, "Z": { "Min": 0, "Max": 0 } }, "Opacity": 0 }
    },
    "InitialAnimationFrame": {
      "Rotation": { "X": { "Min": 0, "Max": 0 }, "Y": { "Min": 0, "Max": 0 }, "Z": { "Min": 0, "Max": 0 } },
      "Scale": { "X": { "Min": 0.7, "Max": 0.7 }, "Y": { "Min": 0.6, "Max": 0.6 } },
      "Opacity": 1,
      "FrameIndex": { "Min": 0, "Max": 0 }
    }
  },
  "UVMotion": { "Texture": "Particles/Textures/UVMotion/FlowMap.png", "Scale": 1.4, "Strength": 0.2, "SpeedX": 0.32, "SpeedY": 0.83 }
}
```

#### 3. The Particle System

Create a `.particlesystem` file at:

```
Server/Particles/Portals/MyMod_PortalOverlay_D01.particlesystem
```

The system declares one spawner reference at offset `Z: 0.05` (just in front of the portal column) and a `LifeSpan` of 1.5 seconds:

```json
{
  "Spawners": [
    { "SpawnerId": "MyMod_PortalImage_D01", "PositionOffset": { "X": 0, "Z": 0.05 } }
  ],
  "LifeSpan": 1.5,
  "CullDistance": 50.0,
  "IsImportant": false
}
```

#### 4. Hook It Up

Add the system id to your instance config:

```json
{
  "PortalParticleId": "MyMod_PortalOverlay_D01"
}
```

That's it. Players who summon this instance see the image floating in front of the portal block until the destination world is gone.

### Tuning the Position

The `Z` offset on the spawner reference inside the `.particlesystem` file controls how far in front of the portal column the image floats. `0.05` lines up tightly with the vanilla `MagicPortal` particle, larger values float the image further out. Tune per-instance if you want a different look.

## Modes

Modes let you ship multiple difficulty or rule variants of the same instance. A player picks a mode before entering, the framework installs it on the freshly created world, and the runtime applies the mode's effects (mob/boss scaling, drop list and block spawner swaps, death-pipeline overrides, HUD tag, etc.).

The implicit `Default` mode is always present and applies no modifiers (unless server owners edit it). If you only want one set of rules per instance, leave `Modes` out and ignore the rest of this page.

### Top-Level Mode Fields

These are developer-only metadata. They are never written to the player-editable modifier config and cannot be tuned by server owners.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `DisplayNameKey` | Translation key | None (tag hidden) | Translation key for the mode tag shown on the instance HUD while this mode is active |
| `DisplayNameColor` | Hex color | `#d3384e` | Color of the mode tag text |
| `Modifiers` | Object | `{}` | Runtime tunables applied to the world while this mode is active (see below) |

### Modifiers

All `Modifiers` fields are optional. Omit a field to leave its behavior at vanilla.

#### Mob and Boss Scaling

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `MobHealthMultiplier` | Number | `1.0` | Multiplier applied to NPC max health at spawn time |
| `MobDamageMultiplier` | Number | `1.0` | Multiplier applied to outgoing NPC damage |
| `BossHealthMultiplier` | Number | `1.0` | Same, but for entities tagged with `BossComponent` |
| `BossDamageMultiplier` | Number | `1.0` | Same, but for entities tagged with `BossComponent` |
| `BossKillRewardsAsDrops` | Boolean | `true` | When `true` (default), boss kill rewards drop at the boss's death position as per-player owned item entities. Set `false` to give rewards directly to each contributor's inventory instead |
| `RemoveSpawnReturnPortal` | Boolean | `false` | When `true`, removes the auto-placed return portal block from the instance spawn point. Useful when the only exit should be through a boss door or another mechanism |
| `DisableNpcFriendlyFire` | Boolean | `true` | When `true` (default), NPC-on-NPC damage is cancelled inside the instance. Set `false` if your dungeon design relies on NPCs attacking each other |

Health scaling fires on entity spawn and on `/instanceconfig mode` mid-run. Damage scaling fires for every damage event inside the dungeon world after vanilla resistance filters but before damage is applied.

#### Time Limit

```json
"Modifiers": {
  "TimeLimitSeconds": 900
}
```

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `TimeLimitSeconds` | Integer | None (use template value) | Override for the portal world's countdown timer in seconds |

Applied at world creation by rewriting the live `PortalWorld` time limit and resetting the remaining-time stamp so the player gets the full new window from the moment of entry. Only takes effect on entry, mid-run mode flips deliberately do not retune the timer (otherwise a player could extend a run by toggling modes). Setting this on `Default` overrides the baseline for all entries that don't queue a different mode.

`null` (the default) leaves the value declared by the instance template alone.

#### PvP

```json
"Modifiers": {
  "IsPvpEnabled": true
}
```

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `IsPvpEnabled` | Boolean | None (use template value) | Toggles `WorldConfig.IsPvpEnabled`, the flag vanilla `DamageSystems` checks before letting one player damage another |

Applied at world creation and reapplied on `/instanceconfig mode` mid-run flips. The setter mutates the world config directly, which `DamageSystems` reads on every damage event so the change takes effect immediately for any in-flight combat. Setting this on `Default` overrides the baseline for all entries that don't queue a different mode.

`null` (the default) leaves the value declared by the instance template alone.

#### Drop List Replacements

```json
"DropListReplacements": {
  "Drop_Skeleton_Burnt_Knight": "Drop_Skeleton_Burnt_Knight_Hardcore"
}
```

A flat key/value map of `DropList` asset ids: `<originalId>: <replacementId>`. Whenever an NPC inside the dungeon would roll the original drop list on death, the replacement is rolled instead. Omitted keys pass through unchanged so vanilla loot is preserved by default.

Mode changes mid-run via `/instanceconfig mode` apply to every NPC currently loaded, and any NPC killed after the flip uses the new mode's replacement (or the original if the new mode has no entry for that drop list).

##### Authoring a Replacement Drop List

1. Find the original drop list. For vanilla NPCs, look under `lib/Server/Drops/NPCs/...`. For mod NPCs, the modder's pack ships them.
2. Copy the JSON file into your pack under `Server/Drops/NPCs/<New_Id>.json`. The file becomes a new drop list asset whose id is the file name (without `.json`).
3. Edit the contents, change `Weight`, `QuantityMin`/`Max`, swap items, add tiers, whatever. The structure documentation matches vanilla drop list assets.
4. Reference the new id in your mode's `DropListReplacements`.

A typical drop list root looks like:

```json
{
  "Container": {
    "Type": "Multiple",
    "Containers": [
      {
        "Type": "Choice",
        "Weight": 100,
        "Containers": [
          { "Type": "Single", "Item": { "ItemId": "Ingredient_Bone_Fragment", "QuantityMin": 1, "QuantityMax": 3 } }
        ]
      }
    ]
  }
}
```

Container types: `Multiple` (rolls every child), `Choice` (rolls one child by weight), `Single` (one item), `Empty` (no item, used for "nothing" weighted slots).

#### Block Spawner Replacements

```json
"BlockSpawnerReplacements": {
  "MyMod_Common_Chest": "MyMod_Common_Chest_Hardcore"
}
```

A flat key/value map of `BlockSpawner` asset ids: `<originalId>: <replacementId>`. Omitted keys pass through unchanged. The replacement spawner can change anywhere from one to all of:

- The block names that may roll (chest model, alternate skins, decorative variants)
- Per-entry weights (e.g. mimic spawn rate vs. ordinary chest)
- The component data each entry attaches (`ItemContainerBlock.Droplist` for chest contents, `MimicBlock.EntityId` and `MimicBlock.Droplists` for mimic config, etc.)

> **Important timing:** the chosen block bakes into the chunk when the chunk first loads. Mode flips mid-run via `/instanceconfig mode` do **not** re-roll already-loaded chunks, that's intentional for run fairness. Select the mode via `/instanceconfig premode` (or a portal UI) *before* entering the world.

##### Authoring a Replacement Spawner

1. Find the original spawner under `Server/Item/Block/Spawners/...`. The id is the file name without `.json`.
2. Copy the JSON to a new file with your variant's name (typically `<original>_Hardcore.json`).
3. Tune the entries, bump mimic weights, point chest droplists at a `_Hardcore` variant, swap block models. The framework's `MJ_Common_Chest_D01_Hardcore.json` is a good reference.
4. Reference the new id in your mode's `BlockSpawnerReplacements`.

Minimal spawner shape:

```json
{
  "Entries": [
    {
      "Name": "Furniture_Human_Ruins_Chest_Small",
      "Weight": 75,
      "Components": {
        "Components": {
          "ItemContainerBlock": { "Droplist": "MyMod_Chest_Hardcore" }
        }
      }
    },
    {
      "Name": "Furniture_Human_Ruins_Chest_Small",
      "Weight": 25,
      "Components": {
        "Components": {
          "MimicBlock": { "EntityId": "Mimic_Common", "Droplists": ["MyMod_Chest_Hardcore"] }
        }
      }
    }
  ]
}
```

See [Mimic Blocks](./mimic-blocks) for the full spawner format reference.

#### Death Overrides

```json
"DeathOverrides": {
  "RespawnController": "ExitInstance",
  "ItemsLossMode": "CONSUME"
}
```

Installed as a per-world `WorldConfig.deathConfigOverride` at world creation, so the values are scoped to this single instance world without leaking to others that share the same gameplay config. All fields optional, omitting one keeps the value the world already has.

| Field | Type | Description |
|-------|------|-------------|
| `RespawnController` | String enum (see below) | Where the player respawns on death |
| `ItemsLossMode` | String enum (see below) | What happens to the inventory on death |
| `ItemsAmountLossPercentage` | Number 0-100 | Percentage of stack quantity lost on each `DropOnDeath` item, only consulted when `ItemsLossMode` is `CONFIGURED` |
| `ItemsDurabilityLossPercentage` | Number 0-100 | Percentage durability lost on every kept item |

##### `RespawnController` values

| Value | Behavior |
|-------|----------|
| `HomeOrSpawnPoint` | Vanilla. Respawns at the player's home if set, else at the world's spawn point. For an instance world, both are the dungeon entrance |
| `WorldSpawnPoint` | Vanilla. Respawns at the world's spawn point regardless of the player's home setting |
| `ExitInstance` | Custom (this framework). Boots the player out of the instance back to the world they entered from, using the instance's `WorldReturnPoint`. Use this for hardcore-style modes where dying ends the run |

##### `ItemsLossMode` values

| Value | Behavior on death | Behavior on forced eviction (timeout) |
|-------|-------------------|---------------------------------------|
| `NONE` | Vanilla. No items are dropped, no durability loss applied | Inventory preserved |
| `ALL` | Vanilla. The full inventory is dropped to the ground at the death position. Other players can pick the items up. `ItemsDurabilityLossPercentage` still applies to anything that didn't drop | Inventory wiped (drops vanish with the unloaded world) |
| `CONFIGURED` | Vanilla. Selective drop. Only items whose item asset has `DropOnDeath: true` are eligible. `ItemsAmountLossPercentage` decides what fraction of each eligible stack drops, the remainder stays in the inventory. Durability loss still applies | Probability roll against `ItemsAmountLossPercentage` (treated as 0-1), on hit the full inventory is wiped |
| `CONSUME` | Custom (this framework). The full inventory is wiped in place, nothing drops to the ground, surviving teammates cannot scavenge | Inventory wiped |

Creative-mode players are skipped on both paths, mirroring the vanilla death-pipeline behavior.

##### Forced Eviction

The "forced eviction" column covers portal timeout and admin world removal. Voluntary exits via portal or `/leave` always preserve inventory regardless of `ItemsLossMode`.

##### CONSUME Death Screen Text

The vanilla death screen shows "Item Loss Prevented In This World" when `ItemsLossMode` is `NONE`, which is misleading for `CONSUME` runs since items are lost. The framework displays **"You've Lost Everything..."** instead by default. Override the translation key in your locale files to customize:

```
instance.death.ItemLossMode.Consume = Your custom message
```

The full key is `MajorDungeons.instance.death.ItemLossMode.Consume`.

### Mode HUD Tag

Modes with a `DisplayNameKey` show a tag on the custom instance HUD while active. The tag is sourced from the developer's `ModeDefinition` on the asset, never from the player-editable modifier config, server owners cannot rename or recolor the tag. The implicit `Default` mode never has a tag.

`DisplayNameKey` is a translation key, not a raw string. Add it under `Server/Languages/<locale>/<YourMod>.lang`:

```
instance.mode.Hardcore = Hardcore
```

The mod name (filename without `.lang`) becomes the prefix automatically, so the full key in your JSON would be `mymod.instance.mode.Hardcore`.

### Selecting a Mode at Entry

Mode must be chosen before entering the instance, because some effects (notably `BlockSpawnerReplacements`) only apply during initial chunk generation. There are two ways to queue a mode for the next entry.

#### Portal UI

The bundled portal device UI shows a tab row for each declared mode and queues the selection automatically when the player clicks Summon. No extra wiring is required, the picker appears whenever an instance config declares one or more modes alongside `Default`.

#### Admin Command

The framework ships an admin command for manually queuing a mode without a UI:

```
/instanceconfig premode <instanceId> <modeName>
```

Run it from anywhere (overworld, hub, etc.) before stepping into the portal:

```
/instanceconfig premode MyMod_Instance_D01 Hardcore
```

Use `Default` as the mode name to clear the pending value.

#### Mid-Run Mode Switch

Once a player is already inside an instance world, you can flip the mode in place:

```
/instanceconfig mode <modeName>
```

Mob/boss health scaling and drop list swaps are reapplied to every loaded NPC. Death overrides are reapplied to the world's death config. Already-resolved chest blocks stay as they generated, since `BlockSpawnerReplacements` only fires at initial chunk load. To inspect:

```
/instanceconfig mode-get
```

### Server Owner Tuning

Each declared mode gets a server-owner-editable mirror at `mods/DanBagh_DungeonFramework/InstanceModifiers/<group>_<modName>.json` (where `<group>_<modName>` is your plugin's group and name, e.g. `MyGroup_MyMod.json`). Server owners tune multipliers and replacements there without touching your asset pack. Display metadata (`DisplayNameKey`, `DisplayNameColor`) stays under developer control.

#### Versioning

Add an optional top-level `Version` integer to your `InstanceConfig.json`:

```json
{ "Version": 1, "Modes": { ... } }
```

Advancing the version reseeds your declared modes from the new asset values on next load. Server-owner edits to other modes are preserved. Without a `Version` field, only newly declared modes are added, existing entries are never overwritten.

## Locking World Conditions

Sometimes a dungeon should always be in a specific state, like permanent night, a single moon phase, or a frozen game time. These are vanilla Hytale world settings, not framework features, but they pair well with instances.

### Always Night, Paused Time

The simplest path is to set the world's `GameTime` to a night hour and `IsGameTimePaused` to `true` in the instance template (`Server/Instances/<your-id>/instance.bson`):

```json
"GameTime": "0001-01-01T04:00:00Z",
"IsGameTimePaused": true,
```

`04:00` sits inside the night portion of the day cycle. With time paused the sun never rises.

### Locking the Moon Phase

The moon phase is computed from the world's day-of-year and its `TotalMoonPhases` setting. Collapsing the cycle to a single phase is the cleanest way to lock it.

1. Create a custom `GameplayConfig`. Set `Parent` to whichever existing config has the rules you want, then override the `World` block:

   `Server/GameplayConfigs/MyMod_Instance_D01.json`

   ```json
   {
     "Parent": "Default",
     "World": {
       "TotalMoonPhases": 1
     }
   }
   ```

   With `TotalMoonPhases: 1`, every day is moon phase `0` (full moon).

2. Point your portal type at the new gameplay config. Edit `Server/PortalTypes/<your-portal>.json`:

   ```json
   "GameplayConfig": "MyMod_Instance_D01",
   ```

   The portal type's `GameplayConfig` wins over whatever is saved in the instance template, so this is where the override needs to live.

> **Heads up on inheritance.** `Parent` works at the top-level block, not at the field level. If your child declares a `World` block, that block fully replaces the parent's `World` (any field you omit falls back to the WorldConfig Java default, **not** the parent's value). So if your parent config had `AllowBlockBreaking: false` and you want to keep that, copy those fields into your child's `World` block alongside `TotalMoonPhases`. The same rule applies to other top-level blocks like `Death`, `Combat`, and `Plugin`.

## Frequently Asked

**Do mode names need to be a fixed set?**
No. Use any string. The framework treats every name except `Default` as a developer-declared mode. Lookups are case-insensitive in commands and HUD.

**Can I have multiple modes (Hardcore, Insane, Speedrun, ...)?**
Yes, declare each as a key under `Modes`. There's no cap.

**What happens if a player enters without a pending mode?**
The world starts in `Default` and the HUD tag stays hidden.

**Can I run the same instance with two different modes simultaneously?**
Yes. Each player who enters spawns their own world (or shares depending on your `InstanceWorldConfig`), and mode is per-world. Pending mode is keyed by instance id, so set it immediately before each entry.
